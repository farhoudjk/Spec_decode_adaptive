What this run was for

Three changes went into specloop_rt/controllers.py after the first Axis-3 sweep: (1) recalibrate GatedSpec's acceptance threshold from 0.45 to 0.15, since the measured acceptance rate (0.35–0.46) made the old threshold solve to γ≈1 regardless of the gate; (2) push arrival rate to 32 instead of switching to a bigger model, to get a real read on KV pressure without a ~28GB download the environment's disk quota couldn't fit; (4) make the admission cap's queue term trend-aware, so a draining queue loosens the cap sooner than a growing one at the same level. (Fix #3 — gating on accept_rate_cv — and fix #5 — seed averaging — are still open, not attempted here.) This run targets the ten cells most likely to show movement: the reason workload, which already carried the highest KV occupancy in the original sweep, at rate=16 (a direct repeat, to confirm nothing regressed) and rate=32 (new, to test whether higher load pushes KV pressure further).

The bug: tpot_ema is a per-token throughput number wearing a per-request latency name

Traced from full_reason_r32.0's step-level telemetry (steps.jsonl), not inferred from the aggregate metrics.

Root cause, confirmed against raw telemetry

GatedSpec's gate opens when tpot_ema ≥ 0.85 × tpot_slo (0.034s). The true per-request TPOT this run measured was 0.248s (p50) — a 6× breach that should have opened the gate on essentially every step. But the live tpot_ema signal the controller actually reads sat at ~0.0008s the entire run — 300× lower than reality, and comfortably under the gate's threshold every single time it was checked.

The formula, in specloop_rt/vllm_patch/scheduler_patch.py: tpot_ema = step_time / (accepted_tokens_this_step + num_running). At low concurrency this is a reasonable proxy — one token lands per running request per step, so dividing by num_running approximates per-request latency. At the concurrency this cell actually ran (mean 215 requests in flight), the same step produces one token simultaneously for all 215–256 of them: step_time≈0.38s divided by ~484 combined tokens gives per-token GPU throughput, not the ~0.38s each individual request actually waits between its own tokens. The metric shrinks as concurrency rises, in the exact direction that hides the very decode-bound condition GatedSpec exists to detect.

This is not a bug in fix #1 or fix #4 — it predates both, in code neither fix touched. It explains, precisely, why the recalibrated threshold (verified correct in isolation: γ≈2–3 at the observed acceptance rates) never showed up in a real run: the gate that's supposed to let it through never opened.

rate=16: does the trend-aware cap change anything at an already-tested rate?

SLO attainment and e2e p95, original sweep vs. this validation run, all five arms, reason workload at rate=16. If fix 4 changed behavior at a rate we've already characterized, it should show here.

Differences are in the fourth decimal place or smaller — run-to-run noise on identical single-seed 60s probes, not a behavior change. This is the result you want here: a trend term with trend_gain=0.5 only diverges from the level-only law when the queue is actually moving; at a fixed rate that's already found its steady state, there's nothing for it to react to.

rate=32: does more load raise KV pressure?

Mean KV occupancy across all five arms, rate=16 vs rate=32. The dashed line marks 0.80 — where KVAwareAdmit's ceiling starts to bite.

Read

Every arm rose from ~0.365 at rate=16 to ~0.475 at rate=32 — a real, consistent effect of pushing load. static-cap-lo is the exception: its tight cap (16) throttles concurrency regardless of arrival rate, so it stays flat around 0.035–0.036 at both rates — the cap, not the KV cache, is already the bottleneck there. None of the five arms crossed 0.80. Doubling the rate again, to 64, would be the natural next probe — though at rate=32 the system is already so deep in both_bound territory (SLO attainment at or near 0.0 everywhere except static-cap-lo) that a further rate increase mostly stress-tests queueing collapse, not the KV ceiling specifically.
