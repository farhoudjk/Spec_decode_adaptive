Does tree width matter, or just depth?

vLLM's EAGLE proposer only ever had depth (γ, a linear draft chain) — no engine before SGLang exposed a real branching factor. At full scale, across a real open-loop arrival process, the answer is arrival rate decides it, not the model. On dense Llama-3.1-8B, wider trees win at light load (rate=2, 0% of cells favor topk=1) and lose hard once load climbs (rate=12, topk=1 wins 83% of cells). On sparse Qwen3-30B-A3B, topk=1 stays the best choice at almost every load (67–83%) — width rarely helps this MoE target, regardless of rate.

Correction

An earlier 48-cell pilot (fixed synchronous batches, no arrival-rate axis) reported "width monotonically hurts dense, only helps MoE once depth is deep enough." This 576-cell run — the same two models, now driven by a real Poisson arrival process at three rates — does not reproduce that pattern. Dense's relationship with width flips with load; MoE's doesn't move much with either depth or load. The synchronous-batch pilot was measuring a single, unlabeled load regime and generalizing from it. Treat this page as the current answer, not the earlier one.

Reading the grid

rate decides dense

Dense Llama-3.1-8B's optimal width is a clean function of load, not of depth or batch cap. At rate=2 (light), topk=1 never wins a single cell — width 4 or 8 is faster at every depth tested, because the GPU has idle compute the extra verify work slots into for free. At rate=12 (heavy), topk=1 wins 83% of cells — the same extra verify work now competes with a queue, and every branch costs real time. Per-token latency at B=32 steps=4: topk=1 is flat (6.96ms → 6.98ms between rate=2 and rate=4) while topk=8 nearly doubles under the same load change once rate hits 12.

MoE stays narrow

topk=1 wins 72% of all MoE cells overall, and never drops below 67% at any single rate — sparse routing doesn't create the width-loves-depth effect the smaller pilot found. The pilot's "fastest cell in the whole grid is steps=5,topk=8" result does not replicate: at the same depth and rate scaled to the full grid, topk=1 is faster or tied at every batch size tested. Widening helps occasionally at steps=6-8, topk=8 (21-28% win share at rate=4/12) but never decisively.

batch cap, weak effect

Batch cap (B) shifts MoE's topk=1 win-share only 6 points across the whole B=8→32 range (67% → 78%) — much smaller than rate's effect (67%→83% swing). Dense shows more movement with B (17%→39% topk=1 win-share) but rate still dominates: at B=32 rate=2, topk=1 is 0%; at B=32 rate=12, it's 83%. Arrival intensity, not admission cap, is the variable that actually reorders the optimum.

accept rate ≠ speed

Mean acceptance rate falls hard as width grows on both models (e.g. dense steps=3: 40% at topk=1 → 12% at topk=8) — the same acceptance-collapse curve AXIS5 found for depth alone. But mean_accept_length keeps climbing with width even as rate falls (dense steps=3: 2.19 → 2.76 tokens/step across the same range), because a wider tree offers more candidate paths per verify pass. Whether that trade wins depends entirely on whether the GPU has slack to spend on it — which is exactly the rate story above, not a property of the acceptance curve itself.

Method

Each cell restarts the SGLang server with a fixed --speculative-num-steps, --speculative-eagle-topk, and --max-running-requests (the batch cap) — width is launch-time-static in SGLang exactly as depth was in unpatched vLLM (confirmed from adaptive_spec_params.py: SGLang's own live controller refuses to run unless topk∈{None,1}). Load is an open-loop Poisson arrival trace at the given rate (specloop_rt.workload.homogeneous, the same generator this repo's vLLM harness uses for its own --rate flag) — requests are dispatched paced to their arrival timestamp, not fired as a synchronous batch, so the batch cap and the arrival rate are independent axes rather than one number doing both jobs.
