Why this run

The previous validation run (rates 16 & 32) found the recalibrated GatedSpec threshold never got exercised: the gate that opens it reads tpot_ema, and that signal collapsed to ~300× below its true value at 215–256 concurrent requests. One open question from that report was whether the bug is specifically a high-concurrency artifact — the formula divides by accepted_tokens + num_running, so a much smaller denominator might keep the signal usable. Rates 1 and 2 test exactly that: at rate=2 the reason workload is decode_bound (confirmed by every other arm's regime classification) with only 20–30 requests running at a time, two orders of magnitude below the earlier test.

Conclusion: this is not a concurrency-scale artifact

The bug is structural, not a threshold effect of high load. tpot_ema = step_time_ema / (accepted_tokens_this_step + num_running) divides a whole-batch step time by a whole-batch token count on every scale tested — 20 requests or 256. What changes with concurrency is only the batch step time in the numerator (bigger batches take longer per step), which partially offsets the bigger denominator — but the ratio never approaches true per-request TPOT at any concurrency above ~1–2 requests, because the formula is answering "tokens produced per second of GPU time," not "seconds between one request's tokens." The fix from the previous report stands: this needs a genuine per-request measurement, not a rescaled version of the current one.
