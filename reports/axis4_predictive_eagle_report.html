Every controller fired correctly. Not one changed what the GPU finished.

Four fixes followed Axis-3's ties: a TTFT-predictive admission sensor replacing one that could not respond proportionally, an EAGLE3 draft head to give γ real leverage, rates aimed at the measured load knee, and 3 seeds × 300s runs for statistical power. All four are verified working in the step traces. All ten admission and γ comparisons are ties — and the reason is not measurement noise. The one arm that does move the numbers, load shedding, does so only by refusing the work.

Why this settles it despite a noisy SLO metric

On slo_attainment alone this design is underpowered, and it would be wrong to claim otherwise: with n=3 the minimum detectable difference is 0.114 at rate=6 (127% of the 0.090 baseline) and 0.012 at rate=8 (75%). Every observed delta is roughly 10× smaller, so a modest real effect could hide in the seed noise.

But n_finished has zero variance across the five non-shedding arms — not "similar", not "within error", but bit-identical in all six seed×rate combinations. No number of additional seeds can overturn an exact identity. tpot_p50 agrees to within 0.5% against a baseline SD of 0.0009. The null is a property of the system, not a limit of the measurement.

Why the cap cannot work: it follows saturation, it does not cause it

Conditioning the same run on what the cap was doing shows the causality runs backwards from what the controller assumes.

KV occupancy
The measurement

In steps where the predictive cap throttles to ≤8, num_running is 102.0 and KV occupancy is 0.998. In steps where the cap is wide open, num_running is 44.7 and KV is 0.390. Concurrency is higher exactly when the cap is tightest.

The cap is not choking the system; it is reacting to a system already full. Because vLLM never preempts resident requests, max_num_seqs=1 cannot evict the 102 requests already holding KV blocks — it only blocks new admissions into a system with no room. Queueing moves from the engine to the client and total wait is unchanged. This is the same structural limit found for the KV ceiling in Axis-3, now confirmed for the TTFT sensor: on this plant, admission capping is the wrong actuator for both failure modes.

Three fundamentally different speculation policies produce decode latency identical to within 0.5%, against a seed SD of 0.0009. Acceptance here is high and volatile — exactly the regime where an acceptance-tracking γ law should win — and it still does not matter. The likeliest explanation is that at these batch sizes the GPU is already compute-saturated: extra speculative tokens per step cannot convert into extra tokens per second when there is no idle capacity to spend them on.

The shedding arm: a 9.4× "win" that is entirely an artifact

The sixth arm is the only one that can genuinely remove work. It produces the largest numbers in this sweep — and they evaporate once the rejected requests are counted.

Two ways to score the same run

Scored on the requests it chose to admit, the shedding arm reaches SLO 0.155 at rate=8 against a 0.017 baseline — a 9.4× improvement, with TTFT p99 falling from 146s to 3.7s. That is the largest effect anywhere in this project and it clears the 2-SD significance test.

It is also meaningless as stated. That number comes from rejecting 88% of arrivals and completing 276 requests instead of 2390. Counting each rejected request as the SLO failure it is, attainment is 0.018 against the baseline's 0.017 — a 0.3 SD tie. The policy did not serve users better; it served far fewer users and graded itself on the survivors.

This is why slo_attainment_offered and shed_frac were added to analysis.py before this arm ran, with a standing rule: never report a win on slo_attainment when shed_frac > 0. A shedding policy graded only on admitted traffic can always win by admitting less, so the metric has to be fixed in advance or the experiment cannot be trusted.

The bug that nearly hid this entirely

On its first run this arm reported shed_frac = 0.0. Not a policy decision but a defect: the predicate read scheduler state via vllm_patch.last_observation(), and vLLM v1 runs EngineCore in a separate process — the scheduler set that global in the engine process while the predicate ran in the client process and read None every time.

The symptom is indistinguishable from "the policy correctly chose not to shed", so it would have been reported as a legitimate sixth tie. The predicate now uses client-owned state (observed TTFT of admitted requests, plus in-flight requests already past budget), was unit-verified on four cases, and all six cells were re-run.

What this means

Read

The admission-primary thesis does not hold on this plant. Both of its actuators — the TTFT cap and the KV ceiling — can only refuse new admissions. On a system whose concurrency is set by KV capacity and whose resident set is never preempted, that authority is empty: the controller reacts to saturation it cannot relieve.

γ is not a useful control variable here, on either ngram or EAGLE, with acceptance either stable or volatile. Two substrates, one answer.

Shedding is the only lever that moves the needle, and it moves it by doing less work. It is the one arm that changes n_finished at all, because refusing a request is the only action available that actually removes load. On offered load it still ties the baseline, so it is not a controller improvement but a different service-level contract wearing the same metric.

What remains untested is preemption. Every mechanism here can only decide what to admit; none can reclaim a KV block from a running request. On a KV-bound plant with a never-preempted resident set, that is the only remaining place a controller could get real authority — and it is the experiment this sweep argues for next.
