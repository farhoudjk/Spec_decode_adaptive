What each arm isolates, and why shedding needs its own metric

A companion to the results page. Six arms form a chain in which each step adds exactly one mechanism, so any observed difference is attributable to that mechanism alone. This document states each control law with its real parameter values, explains the load-shedding policy and the accounting that keeps it honest, and lists the design decisions that constrain what the results can be read to mean.

6 arms × 2 rates × 3 seeds × 300s Llama-3.1-8B + EAGLE3, RTX A5000 24GB scripts/sweep_predictive.py

The bracketing chain

Each arm differs from the one above it by a single change. This is what makes the ablation interpretable: a null at any link means that mechanism contributed nothing, not that the bundle as a whole failed.

static-cap-hiBaseline
Fixed cap 256, fixed γ=4. The configuration Axis-1/2/3 were all run at. Everything is measured as a delta against this.
ratio-capControl
The old admission sensor (TTFTSlackAdmit). Included so that "the new sensor is better" is a measured claim, not an assumption. Without it, a null from predictive-cap could not be distinguished from "no admission policy ever matters here".
predictive-capTreatment
The new sensor (TTFTPredictiveAdmit). Identical actuation, gain, period, deadband and clamps to ratio-cap — only the slack computation differs. predictive-cap minus ratio-cap isolates the sensor change and nothing else.
predictive-kvAblation +1
Adds the proportional KV ceiling on top (KVPredictiveAdmit), combined as min(ttft_term, kv_ceiling). The delta against predictive-cap is the ceiling's incremental contribution.
predictive-fullAblation +2
Adds gated γ (GatedSpec) on top of that. The delta against predictive-kv is what adaptive speculation depth contributes once admission is already handled.
predictive-shedAblation +3
Adds admission-time rejection. The only arm that can refuse work outright; must be scored on offered load.

Why a losing baseline matters

ratio-cap exists to make the comparison falsifiable. If only static-cap-hi and the predictive arms were run, a tie would be ambiguous between "the new sensor does not help" and "no admission control helps on this plant". Including the old sensor separates those: it ties the static baseline too, and its step trace shows why (the cap moves 256→250 and never binds), which converts the ambiguity into a mechanism.

Control laws, as implemented

All values below are the ones actually used in the sweep, taken from scripts/sweep_predictive.py and specloop_rt/controllers.py. Every loop runs on a period of 4 scheduler steps and clamps its output to [1, 256].

1. Ratio sensor — TTFTSlackAdmit (the old law)

slack = 0.7 − num_waiting / cap
if |slack| > 0.05:  cap ← cap + 0.5 × 8 × slack

The defect is structural, not a tuning error: slack is bounded above by target_util = 0.7, and for any queue shorter than the cap it is small. At the observed peak (207 waiting, cap 256) slack is −0.109, giving a correction of −0.43 per update against a 256-wide cap. The law is mathematically incapable of responding proportionally to a severe TTFT breach.

2. Predictive sensor — TTFTPredictiveAdmit (the new law)

service_s    = est_output_len × tpot_ema
finish_rate = num_running / service_s
pred_wait   = num_waiting / finish_rate     ← Little's Law
budget      = 0.7 × ttft_slo_s            = 1.4 s
slack       = (budget − pred_wait) / budget − 0.5 × trend_ema / budget
if |slack| > 0.05:  cap ← cap + 0.5 × 8 × slack

The sensor now measures the quantity the SLO is written against. Because slack is normalised by the budget rather than bounded by a ratio, it scales with how badly the SLO is being missed: at the same observed step the predictive law computes a 138.6 s predicted wait against a 1.4 s budget, slack = −98, correction = −392 (clamped to the floor). Same gain, same actuation code, roughly 900× the response.

est_output_len is the one workload-specific constant, set from measured mean_output_tokens (316 for code, 840 for reason). The trend term is an EMA (β=0.3) of the change in predicted wait, so a queue that is draining loosens the cap sooner than one still growing.

3. KV ceiling — KVPredictiveAdmit

if kv_used_frac ≤ 0.80:  ceiling = 256
else: over = (kv_used_frac − 0.80) / 0.20
      ceiling = 256 − over × (256 − 0.30 × 256)

cap = min(ttft_term, ceiling)

Combined as min, not a blend, so the two terms stay attributable: KV headroom is a hard bound that TTFT slack may never override. The falloff is proportional rather than a single trip-wire, so admission tightens progressively as pressure builds.

4. Gated speculation — GatedSpec

gate_open = (tpot_ema ≥ 0.85 × tpot_slo_s) and ((1 − kv_used_frac) ≥ 0.15)

if not gate_open:  γ = 1  (floor)
else:  target = log(0.05) / log(accept_rate_ema)
      if |target − γ| > 0.5:  γ ← clamp(γ + 0.5 × (target − γ), 0, 8)

γ is a regime-gated trim, not a primary knob: it only adapts when the system is decode-bound and KV has headroom, and pins to the floor otherwise, so it cannot compete with the admission loop for the same resource.

The threshold is a property of the substrate, not a constant

threshold was re-derived for this pairing, as the code's own comment requires. Measured EAGLE acceptance spans 0.34–0.44, and the setpoint law log(threshold)/log(accept) gives γ 1.76–2.31 at the inherited 0.15 — permanently below the γ=4 baseline, which would have made the comparison unfalsifiable. At 0.05 the target is γ 2.78–3.65, straddling the baseline so the gated arm can land on either side. Carrying over a threshold tuned on a different draft method would have quietly rigged the result.

Load shedding: the policy

Shedding is the only mechanism in this study that can remove work rather than reorder it. It runs in the replay client, at arrival time, before the request is ever submitted to the engine.

A request is rejected if either condition holds when it arrives:

budget = shed_slo_mult × ttft_slo_s    = 1.0 × 2.0 = 2.0 s

(a) mean TTFT of the last 20 admitted requests > budget  (needs ≥5 samples)
(b) ≥5 in-flight requests have waited > budget with no first token

Condition (a) is the steady-state signal: if recently admitted requests are already missing the SLO, a new arrival will miss it too. Condition (b) is the transient one — it catches a queue collapsing now, before any of its victims have reported a TTFT, which (a) alone would lag behind.

Why the signal is client-side, not from the scheduler

The first implementation read the scheduler's StepObservation through vllm_patch.last_observation(). It shed nothing, ever. vLLM v1 runs EngineCore in a separate process (VLLM_ENABLE_V1_MULTIPROCESSING defaults on), so the scheduler populated that global in the engine process while the predicate ran in the client process and read None on every call.

The failure was invisible: shed_frac = 0.0 is indistinguishable from a policy that legitimately chose not to shed, and would have been published as a sixth tie. The rewritten predicate uses only state the client owns — the TTFTs it has observed and the requests it is still waiting on — and was unit-verified on four cases (healthy, sustained breach, queue collapse, and a near-miss that must not trigger) before the cells were re-run.

Load shedding: the accounting

A shedding policy graded only on the traffic it admits can always win by admitting less. The metric therefore has to be fixed before the arm is run, not chosen after seeing the numbers.

slo_attainment
Fraction of finished requests meeting both SLOs. Comparable to every prior round. Inflated by shedding.
slo_attainment_offered
Same numerator, denominator is all arrivals. Each shed request counts as a failure. The number to compare.
shed_frac
n_shed / n_offered. Published always, so a silent zero is visible as a possible bug rather than a result.
slo_attainment         = ok / n_finished
slo_attainment_offered = ok / n_offered     ← shed requests are in the denominator

A shed request produced no tokens and met no SLO, so it belongs in the denominator. Standing rule for this project: never report a win on slo_attainment when shed_frac > 0.

Experimental design

  1. Rates chosen by measurement, not by inheritance. A probe at rates 4/8/16 located the knee: at rate=4 the queue never forms (num_waiting peaks at 0) and at rate=16 the system is in deep overload (TTFT p99 104 s, KV 0.85). Rates 6 and 8 bracket the transition. The earlier rounds' range was inherited from a different workload and model, and sat outside the regime where policies can differentiate.
  2. 300 s runs, not 60 s. In the prior sweeps e2e p95 approached the run length, meaning the queue never reached steady state and every arm was measured mid-transient.
  3. Three seeds, with spread reported on every number. Single-seed comparisons in earlier rounds quoted differences of 0.02–0.03 that are well inside the ±0.07 seed noise measured here.
  4. Matched seeds across arms. Each arm replays the identical arrival trace per seed, so n_finished is directly comparable cell by cell rather than only in aggregate.
  5. Fixed decision rules, recorded before the results arrived (/workspace/followup_rules.md): what counts as significant (2 SD), when to add seeds, and the prohibition on reporting admitted-only SLO for a shedding arm.
Constraint that shapes what this can be compared to

Both public EAGLE heads for Llama-3.1-8B declare max_position_embeddings = 2048, and the reason workload needs up to 3043 tokens — it crashes with a CUDA device-side assert. This sweep therefore runs code (HumanEval, worst case 1254 tokens). Axis-4 is a new baseline, not a continuation of the five prior reason rounds; it answers whether the design can work on a substrate where γ has leverage, not whether it beats those earlier numbers.

What the design can and cannot conclude

Read

Can conclude: that no admission or speculation mechanism tested changes what this system completes. The evidence is not the SLO ties but n_finished, which is bit-identical across all five non-shedding arms in every seed×rate cell — a zero-variance measurement that additional seeds cannot overturn.

Cannot conclude: that the mechanisms are worthless in general. On slo_attainment alone the design is underpowered (minimum detectable difference 0.114 at rate=6, versus a 0.090 baseline), so a modest SLO effect could hide in the noise. The claim is specific to this plant, this workload and these two rates.

Also cannot conclude that shedding is useless. It is the only arm that changes n_finished at all, and it does dramatically improve latency for the requests it accepts. What it does not do is improve service over offered load — it is a different service-level contract, not a better controller, and the distinction only becomes visible because the accounting was fixed in advance.
